# cpp-study

C++17 の学習記録。1日1テーマ、84日間。

ゲームプログラマーを目指して、文法だけでなく「なぜそうなるのか」と
「綺麗に書くにはどうするか」まで含めて記録していく。

## 環境

- C++17
- Visual Studio 2022 / MSVC（主）
- g++ 13（動作確認）
- Windows (x64)

実行結果は上記環境のもの。`long` と `long double` のサイズは処理系依存で、
同じコードでも MSVC と g++ で値が変わる。

## 進捗

| Day | テーマ | 学んだこと |
|:---:|---|---|
| 01 | 型とsizeof | 型のサイズは処理系依存（`long` は MSVC で4byte、Linux/g++ で8byte）。`sizeof` はコンパイル時に決まる演算子で実行コストは無い。符号なし整数のラップアラウンドは規格で定義された動作だが、符号付きオーバーフローは未定義動作。`float` は有効桁が約7桁で、524,288 を超えると `+0.016f` が丸めで消える |
| 02 | 整数の割り算とstatic_cast | 整数同士の `/` は0方向に切り捨て、`%` の符号は割られる側に揃う（C++11以降規格で保証、`(a/b)*b + a%b == a`）。`double` に代入しても計算方法は左右の型で決まるので `static_cast` は割る前に片方へ掛ける。整数の0除算と `INT_MIN / -1` は未定義動作で、SIGFPE による即死のため `try/catch` では捕まらない。小数の0除算は IEEE754 環境では `inf`/`nan` になり、落ちない代わりに静かに伝播する。負の座標を `/ tileSize` するとタイル0番だけ `-31〜31` の63個分になり、マップ左側だけ当たり判定がずれる。切り上げの `(a+b-1)/b` は加算でオーバーフローする弱点があり、`a/b` に `a%b != 0` で1足す形のほうが安全（除算命令は1回に畳まれるため速度は同等）。定数除算はシフトに最適化されるが、符号付きは丸め補正で3命令、符号なしは1命令 |
| 03 | 関数と値渡し | 仮引数は呼び出し側の値をコピーした別の変数なので、関数内で書き換えても呼び出し側は変わらない（変えたいなら参照/ポインタ）。コンパイラは上から読むため、使う前に宣言が必要（宣言と定義は別物）。引数の評価順序は未規定で、`f(next(), next())` は g++ 13 で `2,1`、clang 18 で `1,2` になり警告も出ない。副作用のある呼び出しは文を分けて順序を確定させる。非void関数で return せずに末尾に到達するのは未定義動作で、g++ では `-O0` で Illegal instruction、`-O2` で Segmentation fault と、最適化レベルで壊れ方が変わった。戻り値を捨てても `-Wall -Wextra` では警告が出ない。`int` 引数に `double` を渡すと黙って切り捨てられる（`-Wconversion` で警告）。関数呼び出しはスタックフレームを積み、深い再帰は `-O0` でスタックオーバーフロー、`-O2` では末尾呼び出し最適化で通った。小さい型は値渡しで十分速く、関数分割を性能理由で避けるのは誤り。実践：`damage`/`damege` の1文字違いで別の変数を渡すバグを unused variable 警告で発見した。同じ処理を2か所に書いて片方だけ `< 0` と間違えた。計算と表示を分け、既存の関数（`calculateHpRatio`）を使い回す |
| 04 | 配列とstd::array | |

## ビルド方法

Visual Studio（MSVC）:

```
cl /std:c++17 /W4 /EHsc main.cpp
main.exe
```

g++（動作確認用）:

```bash
g++ -std=c++17 -Wall -Wextra main.cpp -o main
./main
```
